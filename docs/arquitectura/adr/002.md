# [ADR-0002] Uso de Kong como API Gateway para la arquitectura de microservicios

<br>

* **Estado:** Propuesto
* **Decisores:** Arquitectura de Software / Líder Técnico / Product Owner
* **Stakeholders:** Equipo de Desarrollo, Arquitectura, QA, DevOps, Seguridad y equipos consumidores de las APIs
* **Fecha:** 2026-11-10

<br>

---

## 1. Contexto y Declaración del Problema

Como parte de la evolución de la aplicación desde una arquitectura monolítica hacia una arquitectura basada en microservicios mediante el patrón **Strangler Fig**, coexistirán temporalmente funcionalidades implementadas en el monolito y nuevas capacidades implementadas como servicios independientes.

Esta coexistencia introduce la necesidad de contar con un punto de entrada común que permita gestionar y enrutar las solicitudes hacia el componente responsable de atender cada funcionalidad.

Sin una capa de API Gateway, los consumidores necesitarían conocer directamente las ubicaciones y características de los diferentes servicios, generando mayor acoplamiento entre clientes y componentes internos de la arquitectura.

Adicionalmente, conforme aumente el número de microservicios, algunos requerimientos transversales podrían terminar implementándose repetidamente en cada servicio, por ejemplo:

* Autenticación y autorización.
* Control de tráfico.
* Rate limiting.
* Routing.
* Seguridad.
* Logging.
* Métricas.
* Trazabilidad.
* Transformaciones de requests y responses.
* Administración de políticas comunes.

Para evitar esta duplicación y proporcionar un punto controlado de entrada a las APIs, se requiere incorporar un **API Gateway**.

### Restricciones y fuerzas relevantes

La solución seleccionada debe considerar:

* Coexistencia temporal entre el monolito y los nuevos microservicios.
* Compatibilidad con la estrategia de migración mediante **Strangler Fig Pattern**.
* Posibilidad de redirigir progresivamente endpoints hacia nuevos servicios.
* Minimizar el conocimiento de los consumidores sobre la arquitectura interna.
* Centralizar políticas transversales cuando sea técnicamente conveniente.
* Evitar implementar autenticación, rate limiting y políticas similares repetidamente en cada servicio.
* Permitir crecimiento progresivo del número de APIs y microservicios.
* Facilitar automatización y configuración mediante CI/CD.
* Mantener independencia entre las reglas de negocio de los servicios y las políticas de infraestructura.
* Proporcionar mecanismos centralizados de observabilidad y control del tráfico.

---

## 2. Opciones Consideradas

* **Opción 1: Kong API Gateway.** Incorporar Kong como punto de entrada para enrutar y aplicar políticas sobre las APIs expuestas por el monolito y los nuevos microservicios.

* **Opción 2: Implementar un API Gateway propio.** Desarrollar internamente un componente encargado del routing, seguridad y otras capacidades transversales.

* **Opción 3: No utilizar API Gateway.** Permitir que los consumidores accedan directamente al monolito y a los diferentes microservicios.

---

## 3. Decisión Tomada

Decidimos seleccionar la **Opción 1: Kong API Gateway** como punto de entrada para las APIs expuestas por la plataforma.

Kong permitirá desacoplar a los consumidores de la ubicación física de los servicios y proporcionará una capa central para gestionar routing y políticas transversales.

Esta decisión complementa la estrategia de migración mediante **Strangler Fig Pattern**, debido a que permitirá que determinadas rutas continúen siendo atendidas por el monolito mientras otras se redirigen progresivamente hacia nuevos microservicios.

### Razones Principales de la Elección

* **Routing centralizado:** permite determinar qué servicio atenderá cada solicitud sin requerir cambios en los consumidores.

* **Compatibilidad con Strangler Fig:** facilita redirigir gradualmente funcionalidades desde el monolito hacia nuevos servicios.

* **Políticas transversales:** proporciona mecanismos para aplicar funcionalidades comunes sin implementarlas individualmente en cada microservicio.

* **Seguridad centralizada:** determinadas políticas de autenticación, autorización y control de acceso pueden aplicarse en el gateway.

* **Gestión de tráfico:** permite incorporar mecanismos como rate limiting y otras políticas de control de consumo.

* **Extensibilidad:** su arquitectura basada en plugins permite incorporar capacidades adicionales conforme evolucionen las necesidades.

* **Separación de responsabilidades:** los servicios pueden concentrarse principalmente en lógica de negocio mientras ciertas responsabilidades de infraestructura son gestionadas por el gateway.

* **Automatización:** la configuración del gateway puede administrarse como parte de los procesos de despliegue y CI/CD.

## 4. Análisis Comparativo de Opciones (Pros y Contras)

### Opción 1: Kong API Gateway

Kong se incorpora como una capa intermedia entre los consumidores y los diferentes servicios internos de la plataforma.

#### Ventajas

* Proporciona routing centralizado.
* Evita que los clientes necesiten conocer la ubicación interna de los microservicios.
* Se adapta al proceso de migración gradual mediante Strangler Fig.
* Permite aplicar políticas mediante plugins.
* Facilita centralizar determinadas capacidades de autenticación y seguridad.
* Proporciona mecanismos para aplicar rate limiting.
* Permite manejar políticas de tráfico de manera independiente a la lógica de negocio.
* Facilita incorporar nuevos microservicios sin modificar necesariamente a los consumidores.
* Puede integrarse con procesos automatizados de configuración y despliegue.
* Reduce la necesidad de desarrollar componentes propios para funcionalidades estándar de API Management.
* Permite evolucionar progresivamente la configuración conforme aumente el número de servicios.

#### Desventajas

* Introduce un nuevo componente de infraestructura que debe ser administrado y monitoreado.
* Una configuración incorrecta podría afectar múltiples APIs simultáneamente.
* Requiere conocimientos específicos para su configuración, operación y troubleshooting.
* Debe diseñarse con alta disponibilidad para evitar que se convierta en un punto único de falla.
* Debe definirse claramente qué responsabilidades pertenecen al gateway y cuáles deben permanecer dentro de los servicios.
* Un uso excesivo de plugins o transformaciones puede trasladar lógica que debería pertenecer a los servicios hacia la infraestructura.

### Opción 2: Implementar un API Gateway propio

Consiste en desarrollar internamente una aplicación encargada de recibir las solicitudes externas y redirigirlas hacia los servicios correspondientes.

#### Ventajas

* Control completo sobre la implementación.
* Puede construirse específicamente para las necesidades actuales.
* El equipo controla directamente su código fuente y comportamiento.

#### Desventajas

* Requiere desarrollar y mantener funcionalidades que ya existen en soluciones especializadas.
* Incrementa el código propietario que debe mantenerse.
* El equipo sería responsable de implementar aspectos críticos como seguridad, rate limiting, routing, observabilidad y tolerancia a fallos.
* Incrementa el esfuerzo necesario para incorporar nuevas capacidades.
* Puede convertirse en un componente complejo conforme crezca el número de servicios.
* Introduce un costo de mantenimiento continuo que no representa directamente lógica de negocio.

### Opción 3: No utilizar API Gateway

Los consumidores accederían directamente a cada microservicio o al monolito.

#### Ventajas

* Menor complejidad inicial de infraestructura.
* No requiere operar un componente adicional.
* Puede ser suficiente para arquitecturas muy pequeñas con pocos consumidores y servicios.

#### Desventajas

* Los consumidores deben conocer las ubicaciones de los diferentes servicios.
* Incrementa el acoplamiento entre consumidores y arquitectura interna.
* La migración de endpoints entre el monolito y microservicios puede afectar directamente a los clientes.
* Las políticas transversales pueden terminar duplicándose entre servicios.
* Se vuelve progresivamente más difícil controlar el tráfico conforme aumenta el número de microservicios.
* Complica la aplicación consistente de políticas de seguridad y observabilidad.

### Comparación resumida

| Criterio | Kong API Gateway | Gateway propio | Sin API Gateway |
|---|---|---|---|
| Routing centralizado | **Sí** | Sí | No |
| Adecuado para Strangler Fig | **Sí** | Sí | Limitado |
| Desarrollo adicional | **Bajo/Medio** | Alto | Bajo |
| Mantenimiento propio | **Medio** | Alto | Bajo inicialmente |
| Extensibilidad | **Alta** | Dependiente del desarrollo | Baja |
| Políticas mediante plugins | **Sí** | Deben desarrollarse | No centralizadas |
| Desacoplamiento de consumidores | **Alto** | Alto | Bajo |
| Configuración automatizable | **Sí** | Debe desarrollarse | N/A |
| Complejidad operativa | Media | Alta | Baja inicialmente |
| Escalabilidad arquitectónica | **Alta** | Dependiente del diseño | Baja/Media |

## 5. Consecuencias e Impacto

### Positivas (Beneficios)

* Los consumidores tendrán un punto de entrada estable independientemente de si la funcionalidad se encuentra en el monolito o en un microservicio.

* Las rutas podrán modificarse conforme avance la estrategia de Strangler Fig sin exponer necesariamente esos cambios a los consumidores.

* Determinadas políticas de seguridad y tráfico podrán administrarse centralmente.

* Los microservicios podrán enfocarse principalmente en responsabilidades relacionadas con su dominio.

* Nuevos servicios podrán incorporarse progresivamente al esquema de routing.

* La arquitectura tendrá una capa claramente definida para gobernar el tráfico hacia las APIs.

* La configuración podrá integrarse con mecanismos de automatización y CI/CD.

### Negativas / Riesgos (Compromisos)

* Kong se convierte en un componente crítico de infraestructura.

* Debe implementarse una estrategia adecuada de disponibilidad, monitoreo y recuperación.

* El equipo requerirá conocimiento para administrar y diagnosticar problemas relacionados con el gateway.

* Una política o configuración incorrecta podría impactar varios servicios.

* Será necesario administrar la evolución de rutas y configuraciones junto con la evolución de los servicios.

* Existe riesgo de incorporar demasiada lógica dentro del gateway.

### Medidas de mitigación

1. Mantener la lógica de negocio dentro del monolito o los microservicios correspondientes.

2. Utilizar Kong principalmente para responsabilidades de infraestructura como:

   * Routing.
   * Autenticación cuando aplique.
   * Rate limiting.
   * Control de tráfico.
   * Logging.
   * Métricas y observabilidad.
   * Políticas de seguridad.
   * Transformaciones estrictamente necesarias.

3. Mantener la configuración del gateway versionada.

4. Automatizar los cambios mediante procesos de CI/CD cuando sea posible.

5. Implementar monitoreo y alertas sobre disponibilidad, latencia y errores.

6. Evitar que el gateway se convierta en un nuevo monolito mediante plugins personalizados con lógica de negocio.

7. Definir mecanismos de alta disponibilidad acordes con la criticidad de las APIs.

8. Mantener claramente documentada la relación entre APIs, rutas y servicios internos.

### Relación con Strangler Fig Pattern

Kong tendrá un papel importante durante la migración porque permitirá mantener un punto de entrada estable mientras cambia la implementación interna.

Ejemplo de una etapa inicial:

~~~text
                         Consumidores
                              |
                              v
                      +----------------+
                      |  Kong Gateway  |
                      +----------------+
                         /           \
                        /             \
                       v               v
                 /legacy/*          /api/a/*
                     |                 |
                     v                 v
                +---------+       +------------+
                |Monolito |       | Servicio A |
                +---------+       +------------+
~~~

En esta etapa, determinadas funcionalidades continúan siendo atendidas por el monolito mientras una primera capacidad ya ha sido extraída.

Posteriormente, otra funcionalidad puede migrarse:

~~~text
                         Consumidores
                              |
                              v
                      +----------------+
                      |  Kong Gateway  |
                      +----------------+
                      /       |        \
                     v        v         v
               +---------+ +------+ +------+
               |Monolito | |Svc. A| |Svc. B|
               +---------+ +------+ +------+
~~~

Los consumidores continúan utilizando el mismo punto de entrada.

El cambio ocurre detrás del gateway mediante la modificación controlada del routing.

Cuando finalice la migración de una capacidad:

~~~text
ANTES

Consumidor
    |
    v
Kong
    |
    v
Monolito


DESPUÉS

Consumidor
    |
    v
Kong
    |
    v
Microservicio
~~~

De esta manera, Kong funciona como una pieza habilitadora de la estrategia Strangler Fig.

### Responsabilidades del Gateway y los Microservicios

Es importante evitar trasladar lógica de negocio hacia Kong.

#### Responsabilidades apropiadas para Kong

~~~text
Kong
 ├── Routing
 ├── Autenticación / políticas de acceso
 ├── Rate Limiting
 ├── Traffic Management
 ├── Logging / Observabilidad
 ├── Políticas de seguridad
 └── Transformaciones técnicas necesarias
~~~

#### Responsabilidades de los microservicios

~~~text
Microservicio
 ├── Reglas de negocio
 ├── Validaciones de negocio
 ├── Persistencia
 ├── Procesos del dominio
 ├── Integraciones propias del dominio
 └── Consistencia de sus datos
~~~

Esta separación evita que Kong se transforme en un componente altamente acoplado a las reglas funcionales de la aplicación.

## Conclusión

Se selecciona **Kong API Gateway** como punto de entrada para las APIs debido a que proporciona las capacidades necesarias para gestionar el tráfico entre consumidores, el monolito existente y los nuevos microservicios.

Su incorporación está particularmente alineada con la estrategia definida mediante **Strangler Fig Pattern**, ya que permite mantener estable la interfaz expuesta hacia los consumidores mientras la implementación interna evoluciona progresivamente.

La arquitectura propuesta permite desacoplar:

> **Consumidor → Gateway → Implementación interna**

en lugar de establecer:

> **Consumidor → Implementación específica**

Esto permite que una funcionalidad inicialmente atendida por el monolito pueda ser posteriormente atendida por un microservicio mediante cambios controlados en el routing, reduciendo el impacto sobre los consumidores.

La decisión no implica trasladar la lógica de negocio hacia Kong. El gateway será utilizado principalmente para **routing, seguridad, control de tráfico y capacidades transversales**, mientras que las reglas de negocio continuarán siendo responsabilidad de los servicios correspondientes.

Por estas razones, Kong proporciona un balance adecuado entre **desacoplamiento, seguridad, extensibilidad, gobernanza y compatibilidad con la estrategia de migración gradual** definida para la plataforma.
